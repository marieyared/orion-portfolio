Orion · Engineering Spec

From a one-off review to a reproducible engine

This spec turns the qualities of an expert portfolio review — context-rich, rule-aware, specific — into two stackable layers you can ship into Orion: (A) an expanded investor-profile intake and (B) a deterministic findings engine. The intake supplies the context the review depended on; the engine supplies the domain rules. Together they feed a synthesis prompt so the output is reproducible for users who can't prompt an AI themselves.

The one-paragraph mental model

Three layers, executed in order. Intake collects facts only the user knows (tax domicile, goal, constraints). The findings engine runs pure functions over holdings + intake and emits structured, auditable findings (rules, not opinions). The synthesis prompt receives both and writes the memo. Anything that is a rule lives in code so it is always correct; anything that is judgement lives in the prompt. Prompting is the last layer, not the first.

0

Why split it this way

Orion already computes the quantitative scaffolding (look-through geo/sector via state.geoAgg/state.sectorAgg, concentration, a risk sub-score model, scenario shocks, bond-duration provenance). What it lacks is the personal/tax context that makes advice specific and the encoded rules that catch estate-situs, wrapper, redundancy, and drift issues. The current houseView prompt even admits it: "this user has NOT given a full financial picture (goals, horizon, tax, income)." You can't prompt your way to estate advice you don't have inputs for.

Keeping rules in deterministic functions (not the LLM) buys three things: the numbers are always correct, every finding is auditable to a line of code, and the model can't hallucinate a $60k threshold or invent a withholding rate. The model's job shrinks to what it's good at: weighing, sequencing, and explaining.

A1

Expansion A · The investor-profile data model

Add a new top-level state object, state.investorProfile, kept distinct from the existing state.riskProfile (the 4-question risk score). The risk score stays as-is and feeds the strategic baseline; the investor profile carries the context the review ran on. All fields are optional and nullable so partial profiles degrade gracefully — the engine simply skips rules it lacks inputs for.

// New canonical shape. Lives alongside state.riskProfile.
// Every field nullable; null means "unknown" — never assume a default that changes advice.
state.investorProfile = {

  spendingCurrency: null,   // "USD" | "EUR" | "CHF" … the wallet that ultimately matters
  eventualBeneficiaryCountry: null, // where the book is heading (FX transmission)

  returnObjective:  null,   // "preserve" | "income" | "balanced_growth" | "beat_benchmark"

  horizonYears:     null,   // integer; can mirror risk-Q1 but stored explicitly

  annualIncomeUSD:  null,   // stable income outside the portfolio

  nearTermCashNeedUSD: null, // money needed within ~2 yrs → cash buffer floor

Expansion A · The intake flow

Extend the existing risk-questionnaire modal into a two-part flow. Part 1 is the current 4-question RQ_QUESTIONS risk score (leave it untouched). Part 2 is a new PROFILE_QUESTIONS set — short, single-tap where possible, with sensible "prefer not to say / unknown" escapes so a user can stop early. The intake's job is to fill state.investorProfile, not to score.

// Add inside the PROMPTS object, near _assetMix / _bondDurationLine.
_profileBlock(p) {

B1

Expansion B · The Finding object

Every rule returns zero or one (occasionally several) Finding objects with a uniform shape. Uniformity is what lets the UI render them, the orchestrator sort them, and the prompt consume them without special-casing.

/**
 * @typedef {Object} Finding
 * @property {string}  id         stable slug, e.g. "us_situs_estate"
 * @property {string}  title      one line, human-readable
 * @property {"high"|"medium"|"low"|"info"} severity
 * @property {string}  body       1–3 sentences of plain explanation
 * @property {number=} valueUSD   the dollar amount the finding is about
 * @property {number=} costUSD    estimated $ cost/exposure (for ranking + memo)
 * @property {Object[]} evidence  [{label, value}] — auditable inputs
 * @property {string=} action     concrete, specific suggested move
 * @property {boolean} userDecision  true = it's the user's call, don't decide for them
 * @property {string=} disclaimer  rule-specific caveat (e.g. "confirm with cross-border counsel")
 */
Why userDecision matters

The best reviews refuse to decide what is genuinely the owner's call (e.g. "what's gold's target weight?") while being decisive about what is objectively a fix (estate-situs overage). This flag carries that distinction all the way to the prompt, which is told to present the trade-off and hold the user accountable to choosing rather than picking for them.

B2

Expansion B · Detection helpers

Shared, conservative classifiers. They lean on the ISIN you already store on holdings (h.isin) and fall back to a manual override flag rather than guessing wrongly.

// US-situs = US-listed individual securities + US-domiciled funds (ETFs/ETPs).
// Irish (IE) / Luxembourg (LU) UCITS are NOT US-situs. Treasuries are situs;
// most corporate bonds are NOT. When unsure, mark unknown — never silently assume.
function domicileOf(h) {
  const isin = (h.isin || "").toUpperCase();
  if (h.manualDomicile) return h.manualDomicile;       // user override wins
  if (isin.startsWith("US")) return "US";
  if (isin.startsWith("IE") || isin.startsWith("LU")) return "UCITS";
  if (isin.length === 12) return isin.slice(0,2);        // other ISO-2 prefix
  return "UNKNOWN";
}

function isUSSitus(h) {
  const d = domicileOf(h);
  if (h.type === "equities")              return d === "US";       // US-listed single stock
  if (h.type === "crypto" && h.isin)    return d === "US";       // US-domiciled spot ETF (IBIT)
  if (h.assetClassIsFund || h.type === "etf") return d === "US";  // US-domiciled fund
  return false;                                            // cash, RE, non-US bonds → out of scope
}

function pctOf(valueUSD, total) { return total ? (valueUSD/total*100) : 0; }
Heuristic, by design

These classifiers are good enough to flag, never to file. Every situs/tax finding must carry the disclaimer that the actual treatment depends on domicile, treaties, and account structure, and must be confirmed with a cross-border tax professional. The engine surfaces the question; it does not give the legal answer.

Expansion B · The rule functions

Each is a pure function (holdings, ctx) => Finding[] where ctx bundles {total, classes, sectorAgg, geoAgg, profile, baseline}. Stubs below are wired to your real data shapes and are deliberately conservative.

1 · US-situs estate exposure high

function f_usSitusEstate(holdings, ctx) {
  const p = ctx.profile;
  if (!p || p.isUSPerson !== false) return [];      // only fires for confirmed non-US persons
  const situs = holdings.filter(isUSSitus);
  const exposed = situs.reduce((a,h)=>a+(h.current||0), 0);
  const line = p.ceilings?.usSitusUSD ?? 60000;       // statutory NRA exemption
  if (exposed <= line) return [];
  const over = exposed - line;
  const estTax = [Math.round(over*0.26), Math.round(over*0.40)]; // marginal band
  const keep = new Set((p.convictionHolds||[]).map(s=>s.toUpperCase()));
  const reWrap = situs.filter(h => !keep.has((h.symbol||h.name||"").toUpperCase()));
  return [{
    id:"us_situs_estate", severity:"high", userDecision:false,
    title:`US-situs assets $${fmt(exposed)} — $${fmt(over)} over the $${fmt(line)} line`,
    body:`As a non-US person, US-situs assets above $${fmt(line)} can face US estate tax up to 40%. `+
         `Re-wrapping US-listed names into the UCITS ETFs already held removes situs while keeping exposure.`,
    valueUSD: exposed, costUSD: estTax[1],
    evidence: situs.map(h=>({label:h.name, value:`$${fmt(h.current)} (${domicileOf(h)})`})),
    action: `Convert ${reWrap.map(h=>h.symbol||h.name).join(", ")} into UCITS S&P/Nasdaq wrappers; `+
            `keeps ${[...keep].join(", ")||"core"} untouched and drops situs below the line.`,
    disclaimer:"General NRA rules; no US treaty assumed. Confirm with cross-border tax counsel before acting."
  }];
}

2 · Wrapper / dividend-withholding drag medium

function f_wrapperWithholding(holdings, ctx) {
  const p = ctx.profile;
  if (!p || p.isUSPerson !== false) return [];
  const usFunds = holdings.filter(h => (h.assetClassIsFund||h.type==="etf") && domicileOf(h)==="US");
  if (!usFunds.length) return [];
  const v = usFunds.reduce((a,h)=>a+(h.current||0),0);
  return [{
    id:"wrapper_withholding", severity:"medium", userDecision:false,
    title:`$${fmt(v)} in US-domiciled funds — 30% dividend withholding vs 15% via UCITS`,
    body:"US-domiciled funds withhold US dividends at 30% for many non-US holders; an Irish UCITS equivalent typically reduces this to 15% and removes US estate situs.",
    valueUSD:v, evidence: usFunds.map(h=>({label:h.name, value:`$${fmt(h.current)}`})),
    action:"Prefer the Irish-domiciled UCITS share class of the same index for future buys and re-wraps.",
    disclaimer:"Withholding depends on the holder's treaty position; confirm specifics."
  }];
}

3 · Single-risk-engine concentration medium

// Diversification by ticker count is not diversification by risk factor.
// Sum everything that draws on the same US mega-cap engine: S&P + Nasdaq +
// covered-call income funds + US tech singles. Reuse your sector look-through.
function f_factorConcentration(holdings, ctx) {
  const usLargeCap = pctOf(ctx.geoAgg?.["United States"]||0, 100); // geoAgg already a %
  const tech = (ctx.sectorAgg?.["Technology"]||0) + (ctx.sectorAgg?.["Communication Services"]||0);
  const findings = [];
  if (usLargeCap >= 40) findings.push({
    id:"factor_us_engine", severity:"medium", userDecision:false,
    title:`~${usLargeCap.toFixed(0)}% of equity rides one US large-cap engine`,
    body:"S&P, Nasdaq, income-overlay funds and US single names mostly draw on the same ~30 mega-caps. A US tech drawdown hits most of them at once, regardless of ticker count.",
    valueUSD: Math.round(usLargeCap/100*ctx.total),
    evidence:[{label:"US (look-through)",value:`${usLargeCap.toFixed(0)}%`},
              {label:"Tech+Comms",value:`${tech.toFixed(0)}%`}],
    action:"Treat ticker-count diversification as cosmetic here; diversify by risk factor (size, geography, style), not by adding more US mega-cap lines."
  });
  return findings;
}

4 · Self-imposed ceiling breach info

function f_ceilingBreach(holdings, ctx) {
  const cap = ctx.profile?.ceilings?.aiTechPct;
  if (cap == null) return [];
  const tech = (ctx.sectorAgg?.["Technology"]||0) + (ctx.sectorAgg?.["Communication Services"]||0);
  if (tech < cap - 2) return [];                       // comfortably under → no finding
  return [{
    id:"ceiling_ai_tech", severity:"info", userDecision:false,
    title:`AI/tech ~${tech.toFixed(0)}% is at your ${cap}% ceiling`,
    body:"You have essentially no room to add AI/tech under your own rule. Adding would require trimming elsewhere first — this is the rule working as intended.",
    action:"Park new AI ideas on a watchlist; only add after trimming an existing tech line."
  }];
}

5 · Product redundancy medium

function f_redundancy(holdings, ctx) {
  const out = [];
  // Acc + Dist of the same index: group by a normalized index key you can derive
  // from the name (strip "Acc"/"Dist"/"Distributing"/"Accumulating").
  const keyOf = n => (n||"").replace(/\b(acc|dist|distributing|accumulating)\b/ig,"")
                          .replace(/\s+/g," ").trim().toLowerCase();
  const groups = {};
  holdings.forEach(h => { (groups[keyOf(h.name)] ||= []).push(h); });
  Object.values(groups).forEach(g => {
    if (g.length > 1 && /s&p|msci|nasdaq|index/i.test(g[0].name)) {
      const v = g.reduce((a,h)=>a+(h.current||0),0);
      out.push({ id:"redundant_index_"+keyOf(g[0].name).slice(0,12),
        severity:"medium", userDecision:false, valueUSD:v,
        title:`Duplicate index exposure: ${g.map(h=>h.name).join(" + ")}`,
        body:"You hold two share classes of the same index doing the same job. If the goal is growth, the distributing class pays taxable income you may not want.",
        action:"Consolidate into the accumulating share class unless you specifically need the distributions." });
    }
  });
  // Income/covered-call product vs a growth mandate
  if (ctx.profile?.returnObjective && /growth|beat/.test(ctx.profile.returnObjective)) {
    holdings.filter(h => /equity premium income|covered call|buywrite|qyld|jepi|jepq/i.test(h.name))
      .forEach(h => out.push({ id:"income_in_growth", severity:"low", userDecision:true,
        title:`${h.name} caps upside in a growth mandate`, valueUSD:h.current,
        body:"A covered-call income product trades away upside for yield — the opposite of a pure-growth objective.",
        action:"Decide deliberately: keep as a volatility dampener, or swap for plain growth exposure." }));
  }
  return out;
}

6 · Drift vs decision info / medium

// A position that has grown well past its strategic target is there "by drift,
// not decision." Compare current weight to the risk-profile baseline weight.
function f_drift(holdings, ctx) {
  if (!ctx.baseline) return [];
  const out = [];
  Object.entries(ctx.classes).forEach(([cls, usd]) => {
    const cur = pctOf(usd, ctx.total);
    const tgt = ctx.baseline.class?.[cls];
    if (tgt == null) return;
    const gap = cur - tgt;
    if (Math.abs(gap) >= 8) out.push({
      id:"drift_"+cls.toLowerCase(), severity: Math.abs(gap)>=15?"medium":"info",
      userDecision:true, valueUSD: usd,
      title:`${cls} is ${cur.toFixed(0)}% vs ~${tgt}% target — ${gap>0?"overweight":"underweight"} by drift`,
      body:`This weight may reflect price drift rather than a deliberate choice. If you'd pick ${cur.toFixed(0)}% on a blank sheet today, keep it; if not, it's a rebalancing candidate.`,
      action:`Set an explicit target for ${cls} and rebalance the difference.`
    });
  });
  return out;
}

7 · Idle-cash opportunity cost medium

function f_idleCash(holdings, ctx) {
  const cash = (ctx.classes.Cash || 0);
  if (!cash) return [];
  const buffer = ctx.profile?.nearTermCashNeedUSD ?? Math.min(20000, cash*0.25);
  const idle = Math.max(0, cash - buffer);
  if (idle < 5000) return [];
  const mmfRate = 0.04;                                  // ~T-bill / MMF; refresh from a rate feed if available
  return [{
    id:"idle_cash", severity:"medium", userDecision:false,
    title:`~$${fmt(idle)} idle cash earning near 0%`,
    body:"Cash beyond a sensible buffer is an opportunity cost while short-term rates are ~4%.",
    valueUSD: idle, costUSD: Math.round(idle*mmfRate),
    action:`Keep ~$${fmt(buffer)} as buffer; move the rest into a USD money-market / short T-bill fund at ~4%.`
  }];
}

8 · Goal / structure consistency high

// The central "tension": a defensive-heavy book cannot beat an equity index.
function f_goalStructure(holdings, ctx) {
  const p = ctx.profile;
  if (!p || p.returnObjective !== "beat_benchmark") return [];
  const equity = pctOf((ctx.classes.Equities||0)+(ctx.classes.ETFs||0), ctx.total);
  const defensive = 100 - equity;
  if (defensive < 25) return [];                       // already growth-shaped → no tension
  return [{
    id:"goal_structure", severity:"high", userDecision:true,
    title:`Goal says "beat ${p.benchmark||"the index"}" but ${defensive.toFixed(0)}% is defensive`,
    body:`A book that is ${defensive.toFixed(0)}% in gold/bonds/cash structurally trails an equity index by that block's drag. You can't have maximum safety and index-beating returns from the same book — pick which goal wins.`,
    valueUSD: Math.round(defensive/100*ctx.total),
    action:`Either lift equity toward 70%+ (accepting deeper worst-case drawdown), or change the stated goal to "balanced growth." The engine won't choose for you — but it will hold you to choosing.`
  }];
}
B4

Expansion B · Orchestrator + prompt hand-off

One entry point runs every rule, sorts by severity then dollar impact, and exposes the result to both the UI and the synthesis prompt.

const RULES = [f_usSitusEstate, f_wrapperWithholding, f_factorConcentration,
               f_ceilingBreach, f_redundancy, f_drift, f_idleCash, f_goalStructure];

const SEVERITY_RANK = { high:0, medium:1, low:2, info:3 };

function runFindings(state) {
  const holdings = state.holdings || [];
  const s = buildPortfolioSummary();                    // reuse existing summary
  const ctx = {
    total: s.total, classes: s.classes,
    sectorAgg: state.sectorAgg || {}, geoAgg: state.geoAgg || {},
    profile: state.investorProfile || null,
    baseline: BASELINE[(state.riskProfile && state.riskProfile.profile)] || BASELINE.Balanced
  };
  const findings = RULES.flatMap(fn => { try { return fn(holdings, ctx) || []; }
                                       catch(e){ console.warn("rule failed",fn.name,e); return []; } });
  findings.sort((a,b) => (SEVERITY_RANK[a.severity]-SEVERITY_RANK[b.severity])
                       || ((b.costUSD||0)-(a.costUSD||0)));
  return findings;
}

// Render findings as a compact, auditable block for the synthesis prompt.
function findingsForPrompt(findings) {
  if (!findings.length) return "\nDETERMINISTIC FINDINGS: none triggered.";
  return "\nDETERMINISTIC FINDINGS (computed in code — treat as ground truth, do not recompute):\n"
    + findings.map((f,i) => `${i+1}. [${f.severity.toUpperCase()}] ${f.title}`
        + (f.costUSD?` (~$${fmt(f.costUSD)} at stake)`:"")
        + `\n   ${f.body}`
        + (f.action?`\n   Suggested: ${f.action}`:"")
        + (f.userDecision?`\n   NOTE: this is the user's call — present the trade-off, do not decide for them.`:"")
      ).join("\n");
}

Upgrade the synthesis prompt to consume findings

In PROMPTS.houseView, append both the profile block and the findings block, and add stance instructions that mirror a sharp private-bank memo:

...existing ground-truth block...
${PROMPTS._profileBlock(state.investorProfile)}
${findingsForPrompt(runFindings(state))}

WRITING STANCE:
- Open with a 3-sentence executive summary: what's right, the core tension, the avoidable cost.
- Name specific holdings and dollar amounts. Sequence actions by risk-adjusted impact.
- State trade-offs plainly — no free lunch. If trimming X raises return AND worst-case drawdown, say so.
- Respect every hard constraint in INVESTOR CONTEXT (never suggest selling conviction holds).
- For findings flagged "user's call," present the choice and hold them to picking — don't pick for them.
- End with the single biggest thing you still don't know about their situation.

Optional: a Findings panel in the UI

Because findings share one shape, a list renderer is trivial — map runFindings(state) to cards coloured by severity, each showing title, body, action, and an expandable evidence table. This gives users the rule-based half of the review even before they read the AI memo, and makes every AI claim traceable to a finding.

Testing & guardrails checklist

  • Degrade gracefully. With investorProfile = null, every rule returns [] or skips, and houseView still produces a general memo. No rule should throw.
  • Never invent thresholds. The $60k line, 30%/15% withholding, ~4% MMF rate live in one place each and are commented as assumptions to refresh.
  • Respect constraints. A conviction hold (e.g. NVDA) must never appear in a "sell/convert" action — assert this in Prompt 6.
  • Auditability. Every finding carries evidence[] so any number in the AI memo traces back to a holding.
  • Liability. Keep the existing not-investment-advice disclaimer; tax/estate findings additionally carry their own "confirm with cross-border counsel" caveat. The engine surfaces questions; it does not give legal answers.
  • Staleness. Use completedAt to nudge a profile refresh after, say, 12 months or after a major holdings change.
Note. This is an engineering specification for a software feature, not investment, tax, or legal advice. The rule thresholds and rates shown (the $60,000 US-situs exemption, 30%/15% dividend-withholding figures, ~4% short-rate assumption, estate-tax bands) are illustrative defaults for implementation and must be validated against current law and the end-user's actual circumstances before any output is relied upon. Any portfolio output the feature produces should retain a clear not-a-recommendation disclaimer and direct users to a qualified, licensed professional.
